# D18 产品与优化路线审查

日期：2026-09-29。基线 cba56be7d9a0b1940561d7560fe9a33067df1228，分支 codex/e2-candidate11-blind-eval。用户要求详细解释已有优化、审查卡点、参考成熟产品并更新路线。本轮交付的是证据解释和产品/执行设计优化；没有新增模型调用、真人试用、产品运行时代码、默认替换或部署。

## 1. 结论

方向保留“校园通知 → 正确行动/信息 → 用户核对 → 可靠保存”。执行路径需要调整：先把同一个事实在模型、adapter、评分、确认页面中的含义对齐，把现有分散工程功能合到一条能使用的路径，再用小范围真实操作建立反馈。继续“加 Prompt → 新造十二份模板 → 二十四次比较 → 红项后再加 Prompt”的收益已经受限。

不是所有问题都来自门槛高。D12 已允许分层交付，后续路线却重新把探索放到模型胜出之后；更重要的是评分正在把部分正确事实判成风险，页面仍是旧回放入口，时间指标也不能直接比较手动和辅助。单纯降低分数线或更换更强模型都无法解决这三类问题。

## 3. 为什么一直看不到成效

### 3.1 评分把事实错、表示不同和证据范围混在一起

详见 [D17 追加解释](../../recognition-optimization/candidate17/d17-development/D18_INTERPRETATION_CORRECTION.md)。本轮对两臂录制回答使用同一只读检查：

- S08 的 C17 材料名称、PNG 格式与归属正确，却因多引用动作句失败；上轮将其直接称为新增材料事实错误，表述不准确。
- S10/S11 的 C17 关系端点、方向与生效正确；支持取消/替代的总结句却被参照拒绝。C03 仍有 effective=unknown，真实收益被同一个 relationsPass=false 掩盖。
- S07 Prompt 要提交截止用 submission_deadline，参照只认 task_deadline。模型遵循 Prompt 也会被记严重错误。
- C17 原九个 Severe 标记可分为二个确定工程/事实问题、三个契约/测量问题、四个表示争议。这是 provisional 根因分类，不是新评分；不能宣布“只剩两个错误”。
- S09 的无任务判断正确，但独立停机事件/周三晚漏提；旧 Severe 没反映此真实风险。测试元数据标记遗漏也会让整份失败，重要性却不同。

症结不是能不能做出一个满分工程夹具，而是“多种合理答案都能过、真正有害的最小改动一定不过”。同一作者生成 Expected 和正确夹具的往返，只证明内部可满足，不能证明评分合理。

### 3.2 用户打开的不是新候选路径

src/main.tsx 直接渲染默认 App；src/App.tsx 默认 ProxyDeepSeekExtractionService，src/recognition/prompt.ts 仍为 recognition-2.0.0。Candidate17 当前是实验请求构建器。

6653 在本轮只读 HTTP 检查返回 200，标题为“D15隔离试次 / 匿名工程回放”。src/experiments/candidate16/runtime.tsx 的 execute 明确抛 D13_MODEL_DISABLED。这个页面证明回放/保存，不提供 Candidate17 在线识别。本轮浏览器连接报 nodeRepl.fetch request failed，未完成新点击验收；HTTP 200 不替代浏览器证据，也未检查公开站点当前部署。

今后每项交付必须说明哪个入口、哪个模式、哪个候选。内部可看新候选与正式默认替换是两项不同动作；前者先通过录制 provider 和同一产品组件实现。

### 3.3 确认流程暴露了内部结构

d14-browser.tsx 要求下方打开来源，再返回上方 Tools 编辑事件。先确认事件会改变工作区版本，任务再确认触发重载；D16 已保护未保存字段，但用户多点重载/重新核对。安全实现有用，交互成本仍高。

应以“一份通知的一次核对”为单位。任务、事件、材料和时间共用 ReviewSession 缓冲，同页操作，确认后生成一个原子计划；真实冲突才要求选择，不让普通用户手动操作内部版本。无关部分可保存，但依赖连通的事项必须一起验。

### 3.4 省时指标并未具备可比较输出

src/experiments/candidate16/measurement.ts:24—37 按存储叶路径统计字段；一次用户更改时间可能联动 ID、scope、display，多算“字段”的风险尚需反例验证。d14Trial.ts:39—50 把手动与辅助最终处置及时间混合，只有平均值，不能回答辅助省了多少。

真实负责人、参与者与同意一直为零，四项真人指标不可观测。应先补对照聚合与页面证据，然后用获准小规模探索找操作痛点；不要求模型全面胜出后才开始这项准备。

### 3.5 规划没有落实自己的规则

NEXT_STAGE_EXECUTION_PROMPT 仍要求 D14/D13 的 C03/C16；PROJECT_ENTRYPOINTS 仍指 D12/D13。九份主要规则/规划入口原合计84082字节，反复前插历史“当前”；加项目入口，本轮归档十份文件共85748字节。根规则已经允许探索并行，路线却仍写“开发筛选之后才准备真人探索”。这次把旧正文按原字节归档，活动状态文件只保留一个当前状态。

package.json 的 npm test 在 Vitest 失败后停止，后续 server/worker/functions 未运行；旧 Node 测试被 Vitest 收集、carrier 未注入、全量负载超时一直重复。应统一现行测试编排，保留历史复现失败；不能以跳过失败组换“全绿”。

## 4. 从第一性原理重新定义产品

学生收到一条通知，真正要回答五件事：与我有关吗；我要做什么；何时/满足什么前提才能做；需要什么材料、怎样算完成；以后从哪里找到并继续。结构化 JSON、候选编号、模型调用都只是实现手段。

价值应看“正确办完一份通知付出的总成本”：阅读核对 + 编辑 + 等待 + 恢复 + 错误带来的损失。不能把阅读改字段名称后隐藏，也不能靠全部不选或让用户重填来获得表面安全。

| 稳定职责 | 实现设计 | 为什么 |
|---|---|---|
| 原文与出处 | Source/SourceVersion、文字覆盖、EvidenceRef | 所有建议与纠正可回看 |
| 事实与含义 | 动作对象、交付物、适用性、依赖、生命周期、时间、事件、修订 | 同一事实只有一种权威语义，允许多个 UI 视图 |
| 程序转换 | 唯一 ID 映射、图一致性、反向索引、明确状态推导、时间精度 | 模型不重复维护相同关联；冲突不靠猜 |
| 用户核对 | 来源级 ReviewSession、少量关键摘要、字段依据、局部修改 | 减少跳转与重复确认 |
| 正式保存与行动 | DomainCommitPlan / Repository，今日行动、日历、来源档案 | 可靠保存，任务真正被继续使用 |
| 反馈与观察 | 首次快照、真实纠正、结果裁决、手动/辅助分组 | 用实际失败和工作量决定下一轮投入 |

三个概念必须分开：适用性（我在名单吗）、可开始性（前一步完成了吗）、生命周期（当前/取消/被替代）。原文说“填完后提交”不代表已填完；依赖未知也不代表任务不存在。计划何时做和硬截止亦应分开，个人安排不能覆盖通知截止。保持 v8 canonical，先做兼容服务和新 wire/adapter 契约，不先重写数据库。

## 5. 成熟产品中真正值得借鉴的做法

以下于2026-09-29查阅官方文档；是机制借鉴和本项目推断，不是这些产品能解决中文通知识别的性能证据。本轮未安装库、上传项目数据或启用第三方遥测。

| 资源 | 官方机制 | 本项目采用什么；暂不做什么 |
|---|---|---|
| [Todoist 快速添加](https://www.todoist.com/help/todoist/features/use-task-quick-add-in-todoist-va4Lhpzz)与[截止日期](https://www.todoist.com/help/todoist/features/introduction-to-deadlines-in-todoist-uMqbSLM6U) | 简短录入，自然语言日期；工作日期与硬截止有区别 | 把高频输入做短，日期可改；个人计划不覆盖原文截止 |
| [Linear Triage](https://linear.app/docs/triage) | 进入正式工作前接受、拒绝、暂缓，支持快捷处理 | 收件箱明确“处理/归档/稍后核对”；不照搬自动合并用户来源 |
| [Sunsama 日计划](https://help.sunsama.com/docs/usage-guides/daily-planning/) | 选当日工作、估时、检查工作量 | 保存后给今日下一步；未来再验证估时与日计划，不先做自动全量排程 |
| [Microsoft 人机交互原则](https://www.microsoft.com/en-us/research/project/guidelines-for-human-ai-interaction/) | 能力边界、易纠正、易拒绝、不确定时收窄服务 | 标出具体未知字段，保留人工完成路径；不把模型自报置信分当校准概率 |
| [LangSmith 评估类型](https://docs.langchain.com/langsmith/evaluation-types) | 区分离线基准、回归、实际运行反馈 | 固定回归资产、真实失败反馈；现阶段复用本地工具，不增加云平台依赖 |
| [Promptfoo 断言](https://www.promptfoo.dev/docs/configuration/expected-outputs/) | 可对已有输出直接运行断言，支持不同检查 | 评分改动先重用原始回答，细分检查结果；不为离线复核再发模型请求 |
| [Google LangExtract](https://github.com/google/langextract) | 结构提取、原文定位与可视化 | 借鉴事实与来源区间对照；现有 TS 链优先，不先引入 Python/额外模型及多轮提取 |

本项目差异化应是“中文校园通知的可追溯处置”，而不是复制一套更大的 Todoist/Notion 或增加更多 Agent。OCR、知识问答、周报、项目层级、账号同步以后按真实需求和损失排序。

## 6. 新路线与优先级

完整任务、依赖和验收见 [活动路线](../PROJECT_EXECUTION_ROADMAP.md)，下一整包见 [D19 执行提示词](../NEXT_STAGE_EXECUTION_PROMPT.md)。

1. D19 先用旧 raw 零调用完成三件事：事实/评分契约对齐；统一核对页与来源级事务；按语义字段及手动/辅助分组计量。测试编排是支撑维护项，不能压过主线。交付实际运行入口、浏览器保存/恢复/读回证据和旧输出双臂诊断。不是新候选成绩。
2. 产品探索准备与技术修复并行。材料已经够发现界面问题，不再重复造空表。指定真实负责人，获授权后安排3—5人、每人4条不同匿名通知，手动/辅助平衡。少量样本用于找卡点，不能宣称统计证明。
3. 只有新 Prompt/输入/adapter 有明确变化与可反驳假设时申请付费比较。优先最近候选作对照、C03保留锚点；先冻结后调用。样本规模按覆盖决定，可提出小批机制验证，再用固定集验证退步；任何新增调用须新明确授权，不能沿用D17。
4. 收集真实失败分布后确定文字首发支持契约。候选冻结后做真正未见的独立人工 A/B 参照与质量验证，数量由声明精度和风险决定，不把12个模板等同市场表现。
5. 受限预览与生产分别审批。先验数据备份/恢复、浏览器、主链测试、安全/依赖、实际路由、成本/失败、回退；发布范围之外有清楚人工接管。逐步发布后才验证留存、再使用和长期遗漏。

## 7. 成功、停止与剩余真人材料

下轮成功首先意味着：普通用户在一个入口打开一份混合通知，能看依据、改任务或事件、局部确认、正确归档、保存失败恢复，读回/刷新一致；评分能解释是哪里错；时间能按条件输出。不能只交新 Manifest 或模板。

已证明的错误转换、依据矛盾、原文漏项继续严格处理。争议只阻断相关质量裁决；模型未胜出不阻断安全产品修复。连续小补丁无效应检查接口和状态模型，不自动加提示词。只有有新增发现才追加审查。

用户后续最少需要指定一名真实负责人及小范围探索授权；参与者/同意须真实，通知可继续用已审查匿名材料。独立 Holdout 所需未见材料和 A/B 人工是另一项工作，不要求探索参与者同时担任独立标注者。付费评测按冻结包单独申请；本轮无请求。
