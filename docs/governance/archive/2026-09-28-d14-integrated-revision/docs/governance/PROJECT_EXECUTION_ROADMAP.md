## 下一阶段：两条可分开推进的工作

| 顺序 | 做什么 | 完成产物/停止条件 |
|---|---|---|
| A1，只读准备 | 核新包 SHA/当前账本；查官方 deepseek-flash 路由、峰时计费和 token 上限，证明 24 请求最坏费用 | 一个有金额和依据的授权卡；证明不了就列明具体费用未知，不派发 |
| A2，需新批次授权 | 用户看卡后明确模型/24次/美元硬上限。专用执行器绑定已提交 HEAD 与身份，测试一次发送/跨进程锁/未知状态停发；提交推送后执行 | 24 个结局或安全停发现场；零额外样本、重试、repair、verifier；不复用 D11 grant |
| A3，冻结同口径分析 | 用已冻结 v7 评估 C03/C16，逐来源改善/退步/未知；负责人补审标题/描述和泄漏 | 开发方向结论，不冒充独立质量；关键风险不被平均分抵消 |
| B1，可本地另行授权 | 将已验收链路接入正式 trialId/新库；增加手动条件、退出/暂停、缺失记录，冻结辅助刺激与阈值 | 可操作空试次入口，仍无真人；不复制孤立公式或造假参与者 |
| B2，需真人范围授权 | 用户安排 3—5 人及真实负责人、取得同意；每人4条不同通知，手动/辅助平衡 | 行为与独立读回、暂定人工裁决、修改/阅读/等待分层；小样本不作总体优胜宣传 |

两条工作互不把对方的质量门当总开关。确认体验可以用固定录制输出探索，不必等 Candidate16 模型比较全胜。没有业务调用授权时可核价和做本地接口；没有真人时可准备空入口，不能用自动化时间代替真人。

## 之后如何决策

1. 若新候选有明确改善但仍有风险：保留逐项收益，集中修最频繁、最妨碍整份正确的一至三类根因；另建候选/契约版本，不回改本次结果。有限别名/表示争议单列，负责人先裁决再决定下一版参照。
2. 若正确率不错但修改很慢：优先减少无用展开、重复核对和保存次数，用字段/阅读/等待定位；不继续单纯堆 Prompt。
3. 若全量旧测试超时妨碍开发：单独维护启动条件与性能，保留历史失败。先定位异步等待，不提高全局 timeout 或改锁哈希凑绿。
4. 需要独立质量结论时：候选先冻结，真实独立 A 标注/B 复核未见材料，预注册范围与门槛；Development 与探索只提供设计依据。
5. 准备默认替换/发布时：明确首发支持范围和透明回退，完成服务、浏览器、回滚检查；单独申请默认替换/合并/部署，不整支研究分支直接进入 Production。

不为评分订正重新买旧输出；不每轮重造“新 Holdout”；不将旧净增2门当工程总开关；不为同一低风险改动循环审计。每个交付边界验证、一次必要复核、提交立即推送，再进入有新信息价值的工作。
