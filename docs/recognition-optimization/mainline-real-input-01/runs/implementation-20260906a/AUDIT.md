## 2. 具体实现和作用

- inputReceipt：保存原始读取、逐页终态、校对历史及本次发送范围。换文件身份/改文字会使旧发送快照失效；部分或失败页不能当完整来源。只是本机数据函数，尚未绑定真实OCR或仓储。
- modelWire：投影现有语义Schema，模型不给来源身份、标准时间、selected或稳定ID；本机恢复身份和时间。原始HTTP、原始输出、解析对象与适配结果分开。引用和语义完整校验仍须后续composer/capture，不声称这个适配器单独证明语义正确。
- seenInputs与两测试：仅旧8类人工通知的wire形状回放，使用人工对照，不是live模型预测、盲测或新数据集。没有将其导入真实入口。

## 4. 为什么付费没有启动

已公开核验[人民币价格与上下文](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[Responses参数](https://api-docs.deepseek.com/api/create-response/)。价格输入3、输出9元/百万token；输出上限8192包括推理token。

原方案100000输入上界时，每笔0.373728元、24笔8.969472元，固定预留0.40元。但完整请求65536字节不能直接证明计费输入≤100000；官方分词包也未提供Responses JSON Schema包装到完整计费输入的等价证明。因此原固定预留规则未闭合，不能先调用再观察、不能伪造服务商硬配额。并非证明模型贵、不可用或存在隐藏收费。

独立预算复核找到了更保守的方案，避免要求用户自己找token证明：根据官方1M上下文、[超窗400](https://api-docs.deepseek.com/zh-cn/guides/responses_api/)以及纯文本无工具计费语义，保守按1048576输入、8192输出得到单笔最大3.219456元。此为公开文档的保守推导，非实测账单；参数/价格变化仍须重新核验。

**唯一建议是改用3.30元最坏预留的滚动账本**：每次派发前保证“已经结算的费用上界＋未知请求完整预留＋新请求3.30≤10”。仅完整且核验通过的usage按最高价格结算，才释放多余预留；失败/超时/崩溃/未知用量绝不释放，也不重发。总请求仍≤24，不改变A8/B8及可选C8。任一异常仍停发。实际扣费不可观察时仍写NOT_OBSERVABLE，不能把usage推导价当账单。

它改变了原“每笔0.40元固定不可逆预留”的冻结规则，所以此处只是待批准备选，没有修改原计划、没有实现派发、更没有调用。另只预留3.30×3的三次诊断不能完成A8/B8，不作为优先建议。
