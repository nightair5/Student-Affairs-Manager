# MAINLINE-02-I1 最小闭环检查设计（尚未运行）

唯一问题：同样的旧人工工程响应，通过真实 App 的用户动作能否完整保存并在下游找到？不是测试模型准确率，不宣称G5通过。

## 1. 验证结构和证据

真实 App（新 runtime）→真实首页/IntakePanel → CapturePersistenceService →旧人工识别回调→持久化 Draft →真实收件箱恢复→真实 DraftReviewPanel V2→editConfirmationV2/confirmV2→CanonicalWorkspaceRepository/新IndexedDB→刷新→真实任务中心/首页/日历/详情→canonical JSON。

人工回调、冻结旧夹具、故障注入和新测试数据库是模拟部分；其余必须是实际组件/服务。每项记录开始、预期、真实操作、存储前后读取、失败与边界。直接库里造任务不能代替录入验收，DOM成功提示不能代替canonical读回。

采用旧8类人工工程通知（multi/no-date/vague/information/condition-true/condition-false/condition-unknown/revision），不新建数据集。允许仅在新测试内做结构化内存变形与故障注入，不改原夹具。使用旧42字段口径，新通路应42/42；旧40/42与历史FAIL保持。计分只在存储读取后执行，不进入识别/选择/提交。

## 3. 数字与失败标准

- 同旧工程响应关键字段42/42；原文、首次响应hash不变；默认不该选却选、未确认正式写入、重复、已确认覆盖、关键丢失均0。
- “没有日期而无法确认”在真正无日期案例中0；模糊/冲突被拒绝不算此失败，也不得把它们改称无日期。
- 真人操作时间/模型准确率/商业成功率不测。可记录自动化动作与保存等待，仅称工程诊断日志。
- 明确可用边界：本包证明录入、核对、确认、查找/查看、JSON保存与恢复；不证明正式任务编辑、任务执行操作、ICS、真实提醒或完整产品商业上线。
- 有效任务不能因保守策略全部不选或拒绝；核心场景需真实成功证据与读回。
- 任何错误默认选择、受保护变化、Expected进入决策、测试删除/弱化、稳定默认变化、真实库访问或文件/语义范围扩大立即停止。不得再补关键词“救分”。

## 4. 工程、交付与回滚

执行顺序：现场/保护→先失败复现→最多两轮同根因局部修补→定向/对抗→新无上下文独立审查→一次全量lint/test/build及安全、依赖、隔离/保护检查→实际浏览器A–K适用链→最终保护→单独提交推送并核对远端。新测试不得写旧cache/数据，日志进新临时目录；非部署不运行会加载凭证的检查，不声明被跳过项目通过。

浏览器必须官方控制真实App，逐键输入、显式保存、IndexedDB读回；记录浏览器种类与范围，不冒充Chrome/Edge/手机全面验收。执行时需真实错误日志与读取目标ID，避免误读旧标签页/旧库。

隔离回滚是停止测试入口并保留当前测试库证据，不删除、迁移或恢复用户库；产品稳定入口始终未切换。事务失败按真实repository原子回滚；撤销已成功用户保存不是本包授权。代码失败保留现场并只提交获准审计；成功业务提交可由后续另行授权的非破坏性revert撤回，不自动reset。
